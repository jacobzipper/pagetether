Open protocol · draft 0

An API that only answers a page that is still open.

Once someone reverse engineers a site's private API, they copy its cookies and headers once and script against it forever. pagetether makes that credential perishable. Every request carries a token from a key that changes every epoch, and the only way to get the next key is to still be there.

The problem

Reverse engineer once, replay forever.

A site's frontend talks to a private API. Someone opens DevTools, works out how the frontend authenticates, reproduces it in a script, and pulls data at machine speed with no browser at all.

The frontend runs on a machine the attacker controls, so nothing can prevent this outright. Anything the page can compute, they can compute. The useful question is what a working scraper costs, and whether that cost recurs.

A cookie or a static signing routine

  • Worked out once
  • Valid from anywhere, for as long as the session lasts
  • Unlimited requests per credential
  • Copies cost nothing

A pagetether generator

  • Has to keep running the server's code
  • Dead within one epoch of stopping
  • A fixed number of requests per epoch
  • Copies share one allowance and collide

How it works

A second factor for an API, where the factor is "the page is still running".

  1. 1

    Mint

    The page asks for a generator. Your server decides who gets one: a login, a captcha, a device attestation. The seed is agreed by key exchange, so it never crosses the wire, and the page holds it as a key that script cannot export.

  2. 2

    Sign

    Each request carries a token: a MAC over the method, path, query and body under the current key, plus a counter. It is good for that one request, once.

  3. 3

    Beat

    Before the epoch ends the page proves it holds the current key and receives a fresh challenge and a small random program. The next key is derived from the old key, the challenge, and what the program computes in the page.

  4. 4

    Budget

    Each epoch has a fixed number of valid counters per generator. There is no way to ask for more, and beating early is refused.

The server recomputes the proof, checks the counter has not been used and is under the budget, and that is the whole verification. Failed proofs are rejected before any state is touched, so someone without the key cannot burn counters or get a generator revoked.

Probes: questions for a real page

The program the server sends can call probes: small questions that a genuine browser environment answers one way and an imitation answers another. The bundled examples ask the layout engine to size a box.

The answers are never sent back. They are folded into the next key. A wrong answer produces a wrong key, and the next request fails with the same error as a forged token. There is no verdict to study and nothing to say which answer was off.

Attack lab

Eight things an adversary tries, run for real.

Each run starts a fresh verifier in this tab and plays the attack against it, using a from-scratch port of the client that holds its key in the clear. Time is simulated, so 30-second epochs pass instantly. The last attack succeeds, and that is the point of showing it.

Limits

What it does not do.

It does not stop a real browser under automation.

A scripted browser driving the real page passes every check. pagetether forces a scraper back into a browser and caps what each one can pull. Spotting automated browsers is a separate job, and probes are a place to put those checks.

The bundled probes are examples.

Their answers are in the repository. They stop a naive port and show the mechanism. Bring your own and calibrate them on real traffic before enforcing.

The gate carries real weight.

The budget caps each generator, so a determined attacker runs many. What each one costs to obtain is decided by your mint gate, not by this protocol.

It only covers what is fetched through it.

Data already in the page's HTML, images, navigations and WebSocket handshakes are not protected. Move sensitive data out of the initial HTML.

State lives in one process, for now.

Running several API nodes needs a shared store with an atomic check-and-set. That is not built yet.

It is a draft.

The protocol will change and nobody has audited it. The design document lists the open questions.

Use it

Two files of setup, no dependencies.

Server

import { Tether } from 'pagetether/server';
import { controlRoutes, guard, readBody } from 'pagetether/node';
import { domOracles } from 'pagetether/probes';

const tether = new Tether({
  epochMs: 30_000,     // a key lives this long
  budget: 60,          // requests per epoch
  probes: domOracles,  // expected probe answers
  gate: ({ req }) => isLoggedIn(req),
});
const control = controlRoutes(tether);

http.createServer(async (req, res) => {
  if (await control(req, res)) return;
  const body = await readBody(req);
  if (!guard(tether, req, res, body)) return;
  // your API
});

Page

import { TetherClient } from 'pagetether/client';
import { domProbes } from 'pagetether/probes';

const tether = new TetherClient({ probes: domProbes });

// a drop-in for fetch()
const res = await tether.fetch('/api/prices?page=2');

The verifier is transport-agnostic and runs on Node or any WebCrypto runtime. This page runs it in your browser.
