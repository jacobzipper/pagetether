Open protocol · draft 0

An agent can read all of your JavaScript. It still needs a browser.

Tools now turn any website into an API: record the traffic, hand the JavaScript to a language model, get back a client that calls your private endpoints with no browser at all. pagetether makes that client stop working. Every request carries a token from a key that changes every epoch, and deriving the next key takes a real layout engine and a page that is still open.

The problem

Reverse engineer once, replay forever.

A site's frontend talks to a private API. Working out how it authenticates used to take a person an afternoon in DevTools. Now it is a product category: tools that record a browsing session, give the capture and the scripts to a language model, and return a typed client for the site's private API. The client runs at machine speed with no browser.

Hiding the logic helps less every year, because a model reads through much of what obfuscation does. So pagetether assumes the agent has read everything. The frontend runs on a machine the attacker controls and nothing can prevent a copy outright. The useful questions are what a working scraper has to carry, what it costs, and whether that cost recurs.

A cookie or a static signing routine

  • Worked out once, by a person or an agent
  • Runs anywhere, with no browser
  • Valid for as long as the session lasts
  • Unlimited requests per credential
  • Copies cost nothing

A pagetether generator

  • Has to keep answering the server's questions
  • Needs a browser engine to answer them
  • Dead within one epoch of stopping
  • A fixed number of requests per epoch
  • Copies share one allowance and collide

How it works

A second factor for an API, where the factor is "the page is still running".

  1. 1

    Mint

    The page asks for a generator. Your server decides who gets one: a login, a captcha, a device attestation. The seed is agreed by key exchange, so it never crosses the wire, and the page holds it as a key that script cannot export.

  2. 2

    Sign

    Each request carries a token: a MAC over the method, path, query and body under the current key, plus a counter. It is good for that one request, once.

  3. 3

    Beat

    Before the epoch ends the page proves it holds the current key and receives a fresh challenge, a small random program and two layout scenes. The next key is derived from the old key, the challenge, and what the program and the scenes come to in the page.

  4. 4

    Budget

    Each epoch has a fixed number of valid counters per generator. There is no way to ask for more, and beating early is refused.

The server recomputes the proof, checks the counter has not been used and is under the budget, and that is the whole verification. Failed proofs are rejected before any state is touched, so someone without the key cannot burn counters or get a generator revoked.

Wrong answers fail silently

What the page computes each epoch is never sent back. It is folded into the next key. A client that gets any of it wrong derives a wrong key, and its next request fails with the same error as a forged token.

There is no verdict to study, no score, and nothing to say which answer was off or by how much. An agent iterating on a port gets one bit per attempt, and each attempt needs a fresh generator from your mint gate.

Scenes

Questions with no formula to port.

A check written in JavaScript can be read, and whatever it computes can be recomputed somewhere else. When one large site derived a request header from a rendered animation, the rendering turned out to be an easing curve and two interpolations, and it was ported to three languages. A scene is the opposite bet: nothing in the client says what the answer is.

What a scene is

A small tree of empty boxes and a stylesheet that mixes block flow, floats, flexbox, grid, positioning, cascade layers and custom properties. The page hands it to the browser, reads back where every box ended up, and folds a hash of those numbers into the next key.

Where the answers come from

The server cannot compute them either. Its pool of scenes was baked: 9,000 random scenes were laid out in current Chromium, Firefox and WebKit at nine zoom settings each and in four older releases, and only the ones where all 37 runs agreed to the pixel were kept, with the answer they agreed on. About one in sixteen survives. Baking is one command and a few minutes, so a pool can be replaced as often as you like.

What it takes to answer one

An engine that resolves the cascade and does layout the way browsers do. DOM libraries such as jsdom have no layout and report every box as 0 by 0. The shortest program that answers every scene is a browser engine, which is the thing a headless client was written to avoid.

Attack lab

Nine things an adversary tries, run for real.

Each run starts a fresh verifier in this tab and plays the attack against it, using a from-scratch port of the client that holds its key in the clear, the kind an agent would write. Time is simulated, so 30-second epochs pass instantly. The last attack succeeds, and that is the point of showing it.

Limits

What it does not do.

It does not stop a real browser.

A scripted browser driving the real page passes every check, and so does an AI agent driving one. A browser can also sit beside a headless client and answer its scenes. pagetether makes the scraper carry an engine and caps what each generator can pull. Telling automated browsers from people is a separate job.

Scenes are measured, not proven.

A browser nobody baked against could lay a scene out differently and lock a real visitor out. Start in report mode: the server sends scenes without enforcing them and logs what your visitors' browsers answer. The pool in the repository is an example with public answers. Bake your own and rotate it.

The gate carries real weight.

The budget caps each generator, so a determined attacker runs many. What each one costs to obtain is decided by your mint gate, not by this protocol.

It only covers what is fetched through it.

Data already in the page's HTML, images, navigations and WebSocket handshakes are not protected. Move sensitive data out of the initial HTML.

State lives in one process, for now.

Running several API nodes needs a shared store with an atomic check-and-set. That is not built yet.

It is a draft.

The protocol will change and nobody has audited it. The design document lists the open questions.

Use it

Bake a pool, add two files, no dependencies.

Server

import { Tether } from 'pagetether/server';
import { controlRoutes, guard, readBody } from 'pagetether/node';
import { domOracles } from 'pagetether/probes';
import pool from './pool.json' with { type: 'json' };

const tether = new Tether({
  epochMs: 30_000,      // a key lives this long
  budget: 60,           // requests per epoch
  probes: domOracles,
  scenes: pool,         // baked layout scenes
  sceneMode: 'report',  // log first, then 'enforce'
  gate: ({ req }) => isLoggedIn(req),
});
const control = controlRoutes(tether);

http.createServer(async (req, res) => {
  if (await control(req, res)) return;
  const body = await readBody(req);
  if (!guard(tether, req, res, body)) return;
  // your API
});

Bake

# lay out random scenes in the browsers you
# have, keep the ones they agree on
npm run bake -- --out pool.json \
  --chrome --firefox

Page

import { TetherClient } from 'pagetether/client';
import { domProbes } from 'pagetether/probes';

// scenes are answered by the browser, with
// nothing to configure
const tether = new TetherClient({ probes: domProbes });

// a drop-in for fetch()
const res = await tether.fetch('/api/prices?page=2');

The verifier is transport-agnostic and runs on Node or any WebCrypto runtime. This page runs it in your browser.
